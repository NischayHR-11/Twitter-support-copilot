# Report — Twitter Support Copilot

*Hiver SDE Intern take-home. Brand modeled: @AmazonHelp (see disclosure below).*

## 0. The one disclosure that matters

The real Kaggle *Customer Support on Twitter* dataset requires an
authenticated Kaggle account to download, which the build environment for
this assignment did not have. Every number in this report comes from a
**synthetic dataset built to mirror the real dataset's schema and
@AmazonHelp's documented tone** (`src/generate_data.py`), not from real
tweets. This is the single biggest caveat on everything that follows —
see Section 5 for the full unpacking of what it does and doesn't
invalidate.

## 1. Problem framing

**What "good" means for this brand:** an e-commerce support handle like
@AmazonHelp lives or dies on two things — (a) not making a routine
customer wait for a human when a templated resolution would do, and (b)
never letting an automated system touch anything involving money movement
disputes, account security, or an already-frustrated repeat complainer.
So "good" here is *not* "highest intent-classification accuracy." It's:
high recall on the "this needs a human" cases (a missed escalation is a
brand-damage / trust event), reasonable precision on the same axis (over-
escalating defeats the point of automation), and replies that don't
invent policy the brand doesn't actually offer.

**What I chose not to build:**
- **No fine-tuned classifier.** With 6 intents and a small labeled set,
  a few-shot LLM prompt is simpler, more inspectable, and just as
  accurate as training something bespoke — see Section 2.
- **No vector database / embeddings for retrieval.** TF-IDF over a few
  hundred historical tickets is enough to find near-duplicate complaint
  patterns; a real production system with millions of tickets would need
  embeddings, this one doesn't need the complexity yet.
- **No multi-turn conversation modeling.** The agent classifies and
  responds to a single inbound message. Real support threads have
  back-and-forth; handling that well is a materially bigger problem
  (state tracking, "has this already been offered a refund") that I
  scoped out rather than build half of.
- **No auto-send.** The agent always *drafts*; a human (or a separate,
  much more conservative gate) would approve auto-handled replies before
  they post. This report evaluates draft quality, not "safe to fire and
  forget."
- **77-way Banking77-style intent granularity.** I used 6 intents, not
  Banking77's 77. See decision log #3.

## 2. Results vs. baselines

Three classifiers, evaluated head-to-head on the same fixed random
subsample (n=40, seed=123) of the 204-example golden set, plus the two
cheap baselines run on the **full** 204-example set:

| Classifier | Accuracy (full set, n=204) | Accuracy (subsample, n=40) |
|---|---|---|
| Trivial (majority class) | 15.7% | 10.0% |
| Simple (TF-IDF + Logistic Regression) | 85.8% | 85.0% |
| Gemini (few-shot, `gemini-flash-lite-latest`) | — (not run on full set, cost/time) | **97.5%** |

*(Live numbers, regenerated by every `eval/run_eval.py` run, in
`outputs/results.json` / `outputs/eval_details.csv`.)*

Both real baselines beat the trivial one by a wide margin, and the LLM
classifier clears the strong TF-IDF+LogReg baseline by ~12.5 points on
the same 40-example subsample — but see Section 5.1 for why that gap is
almost certainly inflated by the synthetic corpus's template structure.

**Escalation policy** (binary: escalate vs. auto-handle) on the n=40
subsample: **precision 0.43, recall 0.43, F1 0.43** (3 true positives, 4
false positives, 4 false negatives, 29 true negatives). This is the
weakest number in the repo and worth sitting with rather than explaining
away:
- All 4 **false negatives** were `billing_or_payment` messages
  ("charged twice," "promo code didn't apply") that the generator
  randomly marked escalate-worthy (35% `escalate_rate` for that intent)
  but that contain no keyword from `HIGH_RISK_KEYWORDS` and got high
  classifier confidence (0.85-1.0), so nothing in the policy fired. This
  is failure mode #5 below, caught in the numbers, not just anecdotally.
- 3 of 4 **false positives** are `account_access` messages ("my email got
  changed... this is ridiculous") that the policy always escalates by
  design (`ALWAYS_ESCALATE_INTENTS`), but that the generator's
  probabilistic labeling (55% `escalate_rate` for that intent) happened
  to mark as "should not escalate" for this particular sample. This is
  less a policy failure than a mismatch between a deterministic rule
  and probabilistic ground truth — see Section 5.5.

**Reply quality** (LLM-as-judge, 4 axes, 1-5, n=33 auto-handled examples
in the subsample): groundedness 4.67, correctness 4.85, tone 5.00,
actionability 4.79. High scores across the board, but the judge-vs-human
check below shows the judge over-rewards fluent-but-wrong replies more
than these means suggest.

## 3. Failure analysis — top 5 failure modes

All examples below are real rows from the committed
`outputs/eval_details.csv` (n=40 subsample run, seed 123) — not
hypothetical.

1. **Multi-intent messages get a fluent reply that quietly drops half the
   ask.** id 180, `"hi can you check order #482910334 AND also why was I
   charged twice for it"` → classified `billing_or_payment`, drafted
   reply addresses only the duplicate charge and never touches the order
   status question. The LLM-as-judge scored this 5/5/5/5 (missed it
   entirely); human review caught it (Section 4). *Hypothesis:*
   single-label classification is a structural mismatch for compound
   asks; needs an "extract all intents present" step before drafting.
2. **The escalation keyword list has real, measured blind spots.** All 4
   escalation false negatives (Section 2) are billing/fraud-adjacent
   messages ("I was charged twice... need one of these reversed ASAP")
   with no keyword match and high classifier confidence. *Hypothesis:*
   the keyword list catches the obvious cases (lawyer, hacked) but misses
   the much more common "money moved without my consent" phrasing that
   doesn't use any of those words.
3. **Grounded replies sometimes ground in the wrong retrieved example's
   *resolution type*, not just the wrong intent.** id 88, `"Requested a
   refund 5 days ago and still haven't seen the money back"` → retrieval
   correctly found `refund_or_return` examples, but the top match was a
   "return label expired, here's a new one" ticket rather than a
   "refund pending, here's the timeline" ticket, so the draft reply sends
   an irrelevant new return label instead of addressing the missing
   money. *Hypothesis:* retrieval needs sub-intent/scenario clustering
   within an intent, not just intent-level filtering.
4. **Replies sometimes presume a prior action that was never taken.** ids
   144, 41, and 2 all draft "your refund was already processed X days
   ago" in response to messages that are *asking to cancel/return*, not
   asking about an existing refund's status — the model pattern-matched
   the intent correctly but picked the wrong resolution stage. This
   pulled human correctness scores down (Section 4) more than any other
   single pattern.
5. **The LLM-as-judge under-detects all of the above.** Every case in
   items 1, 3, and 4 was scored 5/5/5/5 (or close to it) by the judge and
   only caught on human re-review. This isn't a classifier problem, it's
   an *evaluation* problem: the judge appears to reward "reply sounds
   like the brand and offers *a* resolution" over "reply resolves *this*
   customer's *specific* ask." See `eval/human_agreement_notes.md` for
   the full breakdown.

## 4. Judge-vs-human agreement

To sanity-check the LLM-as-judge, the author independently re-scored
**all 33** auto-handled examples from the committed run (full coverage,
not a subsample of a subsample — see `eval/human_agreement.py` for why)
on the same 4 axes and 1-5 scale, then compared:

| | Value |
|---|---|
| Exact match, all 4 axes | 75.8% |
| Within-1-point agreement | 93.9% |
| Mean absolute difference — groundedness | 0.24 |
| Mean absolute difference — correctness | 0.30 |
| Mean absolute difference — tone | 0.06 |
| Mean absolute difference — actionability | 0.27 |

Headline read: the judge is well-calibrated on tone (94% exact match) and
noticeably worse on correctness and actionability (85% / 79% exact
match) — exactly the axes where "does this reply actually resolve what
was asked" lives. The 3 biggest disagreements are documented with full
reasoning in `eval/human_agreement_notes.md` and map directly onto
failure modes #1, #3, and #4 above — the judge isn't randomly noisy, it's
*systematically* generous on the one thing this assignment cares about
most (grounded, correct resolution), which is the worst kind of
miscalibration to have in an automated quality gate.

## 5. What's misleading about my headline number

This section is mandatory and I mean it:

1. **The dataset is synthetic.** Every "accuracy" number here measures
   whether the pipeline can recover labels from a corpus *generated from
   a fixed set of ~5 templates per intent*. A classifier — especially the
   TF-IDF baseline — can partially succeed by matching surface n-grams
   that are artifacts of my template writing, not signal that would
   transfer to real, organically-worded tweets. **The gap between the
   Simple baseline and Gemini is almost certainly smaller here than it
   would be on real data**, because templates make the "easy" signal
   easier than real language ever is.
2. **The golden set's "hand-labeling" is mostly not independent human
   judgment.** 186 of 204 rows inherit their label directly from the
   generator's metadata (see `eval/LABELING_NOTES.md`). Only the 18
   hand-authored hard cases represent a human actually deciding a label
   after the fact. A "204 hand-labeled examples" claim technically
   satisfies the assignment's letter but not fully its spirit — flagging
   that explicitly rather than letting it hide in an aggregate number.
3. **n=40 for the LLM classifier and reply-quality numbers is small.**
   Chosen to fit a 15-minute, free-tier-rate-limited reproduction budget,
   not because it's statistically comfortable. Confidence intervals on
   these numbers are wide; treat differences of a few percentage points
   between classifiers as noise, not signal.
4. **The LLM-as-judge and the reply-drafting LLM are the same model
   family (Gemini).** A judge grading its own family's outputs has a
   plausible self-preference bias that a truly independent judge
   (different provider) would control for. I didn't have a second
   provider's free-tier key available in this environment.
5. **Escalation ground truth is also generator-defined — and this
   directly deflates the escalation F1 number.** Ground truth comes from
   a per-scenario `escalate_rate` I hand-picked when writing the
   generator, applied *randomly per example*. The actual policy in
   `src/decide.py`, by contrast, deterministically escalates 100% of
   `account_access` messages. Measured on the n=40 subsample: 3 of the 4
   "false positives" behind the 0.43 precision score are `account_access`
   messages that the generator's coin-flip happened to label
   "should not escalate," even though a real support org would almost
   certainly want *every* account-security message routed to a human
   regardless of how routine it looks in isolation. **The 0.43
   precision/recall/F1 numbers understate how sound the policy actually
   is** — they're partly measuring disagreement between a deterministic
   safety rule and a probabilistic label generator, not a real policy
   failure. (The 4 genuine false negatives — missed billing/fraud
   escalations, Section 3 #2 — are a real gap, not an artifact.)
6. **The judge and the reply-drafting model are the same family
   (Gemini), and the judge measurably over-rewards fluent-but-wrong
   replies** (Section 4) — a 75.8% exact-match rate with human review
   means roughly 1 in 4 quality scores in `outputs/results.json` should
   be read with real skepticism, concentrated specifically on the
   correctness/actionability axes rather than spread evenly.

## 6. What I'd do next with one more week

1. Get real Kaggle data (even a scraped/manual small sample) and re-run
   the entire harness — this is the single highest-value next step and
   would immediately validate or invalidate every number above.
2. Use a genuinely independent LLM (different provider) as the judge to
   remove the self-preference confound in Section 5.4.
3. Expand the escalation risk-keyword list into a small embedding-based
   semantic classifier, per failure mode #5.
4. Add a lightweight multi-intent extraction pass before single-label
   classification, per failure mode #1.
5. Grow the golden set's hand-authored-hard-case fraction — right now
   it's 18/204 (~9%); real independent human labeling should be a much
   larger share before trusting any accuracy number for a hiring/business
   decision.

## 7. Decision log

Non-obvious decisions and why, roughly in the order they came up:

1. **Synthetic data over skipping the assignment's data step entirely.**
   Kaggle auth wasn't available; generating a structurally faithful stand-in
   and disclosing it prominently seemed more honest and more useful than
   either blocking on credentials or silently using unrelated data.
2. **Modeled @AmazonHelp specifically** (not a generic/anonymous brand)
   so the tone-matching part of reply drafting had a real, well-known
   reference style to target, while being explicit the underlying tweets
   are fabricated, not scraped.
3. **6 intents, not Banking77's 77.** Banking77 is banking-specific and
   its granularity (e.g. 12 different card-related intents) doesn't map
   to e-commerce support; building a taxonomy from the target domain's
   actual failure modes seemed more honest than importing an unrelated
   ontology for optional bonus points.
4. **Escalation is rule+threshold hybrid, not a single LLM "should I
   escalate?" call.** An LLM asked to self-assess risk is exactly the
   kind of decision that should have a deterministic, auditable floor
   (hard keyword triggers) under it, not depend entirely on model
   judgment for safety-relevant cases.
5. **Escalated tickets get no drafted reply at all**, not even as a
   suggestion. Drafting a reply for something already flagged risky
   creates an "an AI reply exists, someone might just send it" hazard for
   zero benefit, since a human is already in the loop.
6. **TF-IDF retrieval, not embeddings.** Matches the corpus size (a few
   hundred tickets); embeddings would be over-engineering for this scale
   and add an API dependency to a step that doesn't need one.
7. **The Simple baseline is trained with golden-set texts excluded**,
   to avoid trivial memorization/leakage from training on the exact
   sentences it's later evaluated on.
8. **Baselines run on the full 204-row set; the LLM path runs on a fixed
   n=40 subsample.** Free-tier rate limits and the 15-minute repro budget
   made running the LLM on all 204 impractical; keeping baselines on the
   full set (they're free) rather than shrinking everything to n=40
   preserves at least one high-confidence number.
9. **A fixed random seed (123) for the subsample**, committed to the
   repo, so "reproduce this" means the same 40 examples every time, not a
   different random draw that could quietly change the headline number
   between runs.
10. **Judge scores 4 separate axes (groundedness, correctness, tone,
    actionability) instead of one overall quality score.** A single
    number hides *which* thing is wrong; groundedness specifically
    exists because "grounded in historical resolution" is the assignment's
    explicit ask, not just "is the reply nice."
11. **18 hand-authored hard cases were added to the golden set on top of
    the stratified sample**, specifically because template-generated data
    is too easy (Section 5.1) — without them, the golden set would
    contain almost no examples designed to actually break the classifier.
12. **Escalated-vs-not is evaluated as precision/recall/F1, not just
    accuracy**, because the classes are imbalanced by design (most
    traffic shouldn't escalate) and recall on the escalate class is the
    metric that actually matters for this brand (Section 1).
13. **`.env` for the API key, gitignored**, rather than hardcoding it or
    requiring a cloud secrets manager — matches the "reproduce in <15
    minutes" requirement without adding infra the assignment doesn't ask
    for.
14. **No auto-send / no production deployment code.** The assignment asks
    to "prove the agent is good enough to trust," which is an evaluation
    problem, not a deployment problem; building deployment plumbing would
    have traded eval rigor for scope that wasn't asked for.
